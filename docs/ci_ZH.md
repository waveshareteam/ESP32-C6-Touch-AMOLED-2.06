# CI 策略

[English](ci.md)

GitHub Actions 是本仓库的构建验证权威。工作流构建源码；已提交的工厂镜像
不作为源码构建目标。

## 构建矩阵

| 工作流 | 一方目标 | 框架版本 |
| --- | ---: | --- |
| `esp-idf-examples.yml` | 5 个应用 | ESP-IDF v5.5.5、v6.0.2 |
| `arduino-examples.yml` | 6 个草图 | Arduino-ESP32 3.3.8 |

两个工作流都以 ESP32-C6 为目标。ESP-IDF 矩阵覆盖最新稳定的 5.5 和 6.0
版本线，Arduino 工作流使用本仓库记录的最新受支持稳定 core 基线。
版本、目标、Arduino 开发板管理器 URL 和 FQBN 均从
`config/toolchains.json` 读取。修改该文件会为两个框架选择完整矩阵。

## 发现与路由规则

ESP-IDF 发现仅接受 `examples/esp-idf` 的直接子目录，并要求其中同时存在
顶层 `CMakeLists.txt` 和 `main/`。因此组件测试和库示例不会进入产品矩阵。

Arduino 发现仅接受 `examples/arduino` 的直接子目录，并要求目录名与主
`.ino` 文件同名。`examples/arduino/libraries` 下的内容不参与草图发现。

Pull Request 和 push 会把完整、可识别重命名的差异交给同一个变更路由器：

- 一方项目或草图变更只选择该目标。
- 共享 Arduino 库变更选择全部 6 个草图。
- 工作流、发现脚本、测试或固件打包器变更选择对应框架的全部目标。
- 仓库根目录、示例旁或随仓库提供的库内 Markdown 不选择固件构建。
- `firmware/` 下的文件单独报告，绝不进入默认示例矩阵。
- 无法识别的非文档路径保守地选择两个完整矩阵，并保留在路由报告中。
- 缺失、为空或无法读取的差异会使发现任务失败，不会静默地全量构建或成功空跑。

`workflow_dispatch` 接受目录名、仓库相对路径或 `all`。

始终可见的 `repository-policy.yml` 工作流检查一方中英文配对、双向与同语言
导航、本地链接和锚点、主页结构以及公开文本卫生；主页与豁免契约从
`config/markdown-audit.json` 读取。两条构建工作流同样在每个 Pull Request
上可见，但昂贵矩阵任务只在路由器选中源码构建输入时运行。

## 构建与打包顺序

1. 检出足够历史，以便执行可识别重命名的路由。
2. 运行发现、路由、Markdown 策略和打包工具的 Python 单元测试。
3. 无法读取完整变更范围时按失败关闭。
4. 构建所有被选中的源码目标。
5. 将成功构建结果打包为可烧录 ZIP。
6. 每个 ZIP 作为独立工作流制品保留 14 天。

打包严格位于编译之后。因此，出现 ZIP 制品表示对应源码构建已经成功。

## ESP-IDF 6 兼容性

应用明确以 `esp32c6` 为目标，并使用兼容两个矩阵版本的组件清单。源码不依赖
旧版驱动依赖的偶然传递，并包含已由矩阵覆盖的 ESP-IDF 6 兼容性修改。

CI 失败时，应诊断第一个真实的编译器或依赖错误，而不是最终汇总行。修复源码
或清单中的根因，然后重新运行完整的受影响矩阵。

## CI 不能证明的内容

CI 验证依赖解析、编译和打包，不提供硬件在环验证。显示时序、触摸校准、音量、
传感器方向、电池行为以及睡眠/唤醒行为仍需在发布提升前通过实体板测试。
